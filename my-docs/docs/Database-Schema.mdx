# Database Schema

## 1. Schema

We designed a relational database using **Supabase**, which is built on PostgreSQL. Supabase Auth issues every account's UUID, which is stored in `users.id`; every other table hangs off it directly or through one of the role profile tables. Below is the database schema for the Tutor Management System:

![Entity-relationship diagram of the Tutor Management System schema (dbdiagram.io)](/img/supabase-schema.png)

The tables split into four areas: **identity** (`users` plus one profile table per role), **courses and allocation** (`courses`, `course_volunteers`, `tutor_subject_preference`, `allocation_overrides`, `allocation_drafts`, `allocation_draft_assignments`, `session_excusals`, `session_swaps`), **timetable and time tracking** (`tutor_busy_times`, `hour_entries`, `timesheets`, `timesheet_disputes`), and **reference and audit** (`academic_terms`, `notifications`, `audit_log`).

### Tables Overview

#### `users`

- One row per registered account. The `role` column decides which profile table the account has and which dashboard it sees.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK) — the Supabase Auth user UUID
- `email` (text, required)
- `name` (text)
- `role` (text) — `student`, `tutor`, `educator` or `organiser`

#### `students`

- Profile row for every account registered with role `student`.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)
- `name` (varchar, required)
- `email` (text)
- `student_no` (text, required, unique)
- `degree` (varchar)

#### `tutors`

- Profile row for every account registered with role `tutor`, plus the workload settings used by allocation and payroll. Pay itself is looked up from `academic_level_rates` via `academic_level`, not stored here.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)
- `student_number` (text, required, unique)
- `email` (text, required)
- `name` (text)
- `academic_level` (text) — `third_year`, `honours`, `masters` or `phd`; looks up the tutor's pay rate in `academic_level_rates` and is checked against a course's `course_level`
- `weekly_hour_cap` (integer)

#### `academic_level_rates`

- The hourly rate paid at each academic level — one row per level, shared by every tutor at that level instead of a rate duplicated onto each tutor's row. Edited from the tutors page's rates settings card (`POST /api/tutors/bulk-rates`), read via `GET /api/tutors/rates` and by the hours/budget report and payroll export.
- **Primary key**: `academic_level`
- **Fields**:
- `academic_level` (text, PK) — `third_year`, `honours`, `masters` or `phd`
- `hourly_rate` (real, required, >= 0)

#### `educators`

- Profile row for every account registered with role `educator`.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)

#### `organisers`

- Profile row for every account registered with role `organiser`.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)
- `staff_id` (varchar, required) — generated server-side on registration
- `full_name` (varchar)
- `email` (varchar)

#### `courses`

- A course that may need tutors, with its tutorial/lab schedule and the mark bar applicants must clear.
- **Primary key**: `id`
- **Fields**:
- `id` (smallint, PK)
- `course_code` (text, required, unique)
- `course_name` (text, required)
- `min_mark` (integer, required, 0–100)
- `department` (text, required)
- `hours_per_week` (smallint, required)
- `tutors_needed` (smallint, required)
- `no_of_tutors_assigned` (smallint)
- `tutor_start_time`, `tutor_end_time` (time)
- `Day_of_tut` (text)
- `course_level` (smallint) — minimum academic level a tutor must hold to apply, as a rank (`third_year`=3, `honours`=4, `masters`=5, `phd`=6); set from the organiser's Add/Edit Course form
- `venues` (text) — tutorial rooms, e.g. `"MSL004,005,006"`
- `Day_of_lab` (text)
- `lab_start_time`, `lab_end_time` (time)
- `lab_venues` (text)
- `budget` (numeric)

#### `course_volunteers`

- A student's volunteering for a course, with the mark they self-reported.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK)
- `user_id` (uuid, required, FK → `users.id`)
- `course_id` (integer, required, FK → `courses.id`)
- `mark` (integer)
- `status` (text, required, default `pending`) — `pending`, `approved` or `rejected`
- `created_at` (timestamptz, required, default now)

#### `tutor_subject_preference`

- A tutor's application to tutor a course, ranked by the mark they scored for it.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `course_id` (smallint, required, FK → `courses.id`)
- `status` (text) — `pending`, `approved` or `rejected`
- `Tutor_name` (text) — denormalised copy of the tutor's name
- `tutor_mark` (integer) — the mark the tutor scored for the course
- `Availability` (bool) — whether the tutor is free at the course's scheduled times
- `locked` (bool, required)

#### `allocation_overrides`

- Audit log written when an organiser approves an application that broke a rule — the course was already full, or the tutor would exceed their weekly hour cap.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `organiser_id` (uuid, required, FK → `users.id`) — the organiser who approved the override
- `tutor_id` (uuid, FK → `tutors.id`)
- `course_id` (smallint, FK → `courses.id`)
- `rule_overridden` (text, required) — `course_capacity` or `weekly_hour_cap`
- `reason` (text, required) — free-text justification supplied by the organiser
- `created_at` (timestamptz, required, default now)

#### `allocation_drafts`

- A saved draft of a proposed tutor allocation, which can be edited and later published.
- Read and written by the application API (`server/routes/allocationDrafts.js`): created by auto-allocate, renamed or pruned while open, then published or discarded.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `name` (text, required)
- `created_by` (uuid, required, FK → `users.id`)
- `status` (text, required)
- `created_at` (timestamptz, required, default now)
- `published_at` (timestamptz)

#### `allocation_draft_assignments`

- One tutor–course pairing inside a draft allocation.
- Read and written by the application API (`server/routes/allocationDrafts.js`): proposed by auto-allocate, removed when an organiser prunes an open draft, applied on publish.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `draft_id` (bigint, required, FK → `allocation_drafts.id`)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `course_id` (smallint, required, FK → `courses.id`)
- `explanation` (text)
- `locked` (bool)

#### `session_excusals`

- A tutor excusing themselves from one scheduled session of a course they are approved for.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `course_id` (smallint, required, FK → `courses.id`)
- `session_date` (date, required)
- `reason` (text)
- `created_at` (timestamptz, required, default now)

#### `session_swaps`

- A request to move one session's tutoring duty from one tutor to another.
- Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `course_id` (smallint, required, FK → `courses.id`)
- `session_date` (date, required)
- `from_tutor_id` (uuid, required, FK → `tutors.id`) — the tutor giving up the session
- `to_tutor_id` (uuid, required, FK → `tutors.id`) — the tutor taking it over
- `status` (text, required)
- `requested_at` (timestamptz, required)
- `reviewed_at` (timestamptz)

#### `tutor_busy_times`

- Recurring busy blocks from a tutor's imported class timetable, used for clash checks when assigning courses.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `title` (text) — e.g. the class name
- `day_of_week` (smallint, required, 0 = Sunday through 6 = Saturday)
- `start_time`, `end_time` (time, required)
- `first_date`, `end_date` (date) — the block's active range
- `venue` (text)
- `source` (text, required)
- `created_at` (timestamptz, required, default now)

#### `hour_entries`

- One row per work session a tutor logs; the raw material that weekly timesheets are built from.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK)
- `user_id` (uuid, required, FK → `users.id`)
- `date` (date, required)
- `hours` (numeric, required)
- `start_time`, `end_time` (time)
- `task_type` (text, required, default `Tutoring`)
- `subject` (text)
- `notes` (text)
- `created_at` (timestamptz, required, default now)
- `updated_at` (timestamptz)

#### `timesheets`

- A tutor's weekly submission of logged hours, for organiser sign-off. `entries_snapshot` freezes the hour entries at submission time so later edits can't retroactively change an approved week.
- **Composite primary key**: `(user_id, week_start)`
- **Fields**:
- `user_id` (uuid, required, FK → `users.id`)
- `week_start` (date, required) — the Monday of the submitted week
- `status` (text, required, default `pending`) — `pending`, `approved` or `rejected`
- `submitted_at` (timestamptz, required, default now)
- `reviewed_at` (timestamptz)
- `reviewer_note` (text)
- `total_hours` (numeric)
- `entries_snapshot` (jsonb, required)

#### `timesheet_disputes`

- A dispute raised against a reviewed (approved or rejected) timesheet. Read and written via `/api/timesheet-disputes` — a tutor raises one against their own reviewed timesheet, an organiser resolves it.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `timesheet_user_id` (uuid, required, FK → `timesheets.user_id`)
- `timesheet_week_start` (date, required, FK → `timesheets.week_start`)
- `raised_by` (uuid, required, FK → `users.id`)
- `message` (text, required)
- `resolved` (bool, required)
- `created_at` (timestamptz, required, default now)

#### `academic_terms`

- University terms and recess periods, for term-aware calendar logic. Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `term_name` (text, required)
- `start_date`, `end_date` (date, required)
- `is_recess` (bool, required)

#### `notifications`

- Per-user notification feed. Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `user_id` (uuid, required, FK → `users.id`)
- `type` (text, required)
- `message` (text, required)
- `related_entity` (text) — the kind of record the notification points at
- `related_id` (text)
- `read` (bool, required, default false)
- `created_at` (timestamptz, required, default now)

#### `audit_log`

- Generic audit trail: a before/after snapshot of any edited entity, recorded with the acting user.
- Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `entity_type` (text, required) — the kind of record that changed
- `entity_id` (text, required)
- `action` (text, required)
- `actor_id` (uuid, FK → `users.id`) — the user who made the change
- `before`, `after` (jsonb) — snapshots of the record before and after
- `created_at` (timestamptz, required, default now)

## 2. Deployment

The database is a Supabase project: PostgreSQL for storage plus Supabase Auth for account management. The application server connects through `server/supabaseClient.js` (`@supabase/supabase-js`), configured with the `SUPABASE_URL` and `SUPABASE_ANON_KEY` environment variables.

- **Local development** — the Express server (`npm start`) reads them from `.env`.
- **Production** — the same app is deployed as a Cloudflare Worker (see `wrangler.toml` in the repository root).

Row Level Security is currently disabled on all tables, so the anon key can read and write every table; authorisation is enforced in the route handlers instead of the database.
