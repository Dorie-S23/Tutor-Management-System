# Database Schema

## 1. Schema

We designed a relational database using **Supabase**, which is built on PostgreSQL. Supabase Auth issues every account's UUID, which is stored in `users.id`; every other table hangs off it directly or through one of the role profile tables. Below is the database schema for the Tutor Management System:

![Entity-relationship diagram of the Tutor Management System schema (dbdiagram.io)](/img/supabase-schema.png)

The tables split into four areas: **identity** (`users` plus one profile table per role, `organiser_requests`), **courses and allocation** (`courses`, `course_volunteers`, `tutor_subject_preference`, `allocation_overrides`, `allocation_drafts`, `allocation_draft_assignments`, `session_excusals`, `session_swaps`), **timetable and time tracking** (`tutor_busy_times`, `hour_entries`, `timesheets`, `timesheet_disputes`), and **reference and audit** (`academic_terms`, `notifications`, `audit_log`).

### Tables Overview

#### `users`

- One row per registered account. The `role` column decides which profile table the account has and which dashboard it sees.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK) — the Supabase Auth user UUID
- `email` (text, required)
- `name` (text) — the account holder's full name; registration and the profile page both use a single full-name field
- `cell_phone` (text) — not collected at registration, so this starts as `null`; filled in from the profile page (`/api/profile`), which checks it's a valid South African cell number
- `role` (text) — `volunteer`, `tutor`, `organiser` or `super_organiser`. The educator role was dropped (see [Dev Plan → Roles](./dev-plan.mdx#roles)); legacy `educator` rows may still exist. Accounts created before the Volunteer rename store `student` here; the API accepts it as an alias for `volunteer`. The `super_organiser` value marks the one admin account (promoted by hand — see [Getting Started](./getting-started.mdx#4-set-up-organiser-access-one-off))
- `auth_provider` (text) — `password` or `google`, set at registration

#### `students`

- Profile row for every account registered with role `student`.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)
- `name` (varchar, required)
- `email` (text)
- `student_no` (text, required, unique)
- `degree` (varchar)

#### `tutors`

- Profile row for every account registered with role `tutor`, plus the workload settings used by allocation and payroll. Pay itself is looked up from `academic_level_rates` via `academic_level`, not stored here.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)
- `student_number` (text, required, unique)
- `email` (text, required)
- `name` (text)
- `academic_level` (text) — `third_year`, `honours`, `masters` or `phd`; looks up the tutor's pay rate in `academic_level_rates` and is checked against a course's `course_level`
- `weekly_hour_cap` (integer)

#### `academic_level_rates`

- The hourly rate paid at each academic level — one row per level, shared by every tutor at that level instead of a rate duplicated onto each tutor's row. Edited from the tutors page's rates settings card (`POST /api/tutors/bulk-rates`), read via `GET /api/tutors/rates` and by the hours/budget report and payroll export.
- **Primary key**: `academic_level`
- **Fields**:
- `academic_level` (text, PK) — `third_year`, `honours`, `masters` or `phd`
- `hourly_rate` (real, required, >= 0)

#### `educators`

- Legacy: profile row for accounts registered with role `educator`. The educator role was dropped — no new rows are written (see [Dev Plan → Roles](./dev-plan.mdx#roles)).
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)

#### `organisers`

- Profile row for every account registered with role `organiser`.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK, FK → `users.id`)
- `staff_id` (varchar, required) — generated server-side on registration
- `full_name` (varchar)
- `email` (varchar)

#### `organiser_requests`

- One row per access request, approved or denied by the super-organiser (via `/api/organiser-requests`). Two kinds: `signup` — filed when someone registers as an organiser, where approval grants their chosen course and unblocks their sign-in; `access` — filed from the board by an existing organiser asking for one more course, where approval widens their scope on their next sign-in. A pending or denied `signup` blocks the account at sign-in. Organisers registered before requests existed have no rows here and keep full access to every course.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `user_id` (uuid, required, FK → `users.id`) — the requesting organiser
- `course_id` (smallint, required, FK → `courses.id`) — the course they're asking for
- `kind` (text, required, default `signup`) — `signup` or `access`; rows from before the column exist read back as `signup`
- `status` (text, required, default `pending`) — `pending`, `approved` or `denied`
- `created_at` (timestamptz, required, default now)
- `reviewed_at` (timestamptz) — when the super-organiser approved or denied it
- `reviewed_by` (uuid, FK → `users.id`) — the super-organiser who reviewed it

#### `courses`

- A course that may need tutors, with its tutorial/lab schedule and the mark bar applicants must clear.
- **Primary key**: `id`
- **Fields**:
- `id` (smallint, PK)
- `course_code` (text, required, unique)
- `course_name` (text, required)
- `min_mark` (integer, required, 0–100)
- `department` (text, required)
- `hours_per_week` (smallint, required)
- `tutors_needed` (smallint, required)
- `no_of_tutors_assigned` (smallint)
- `tutor_start_time`, `tutor_end_time` (time)
- `Day_of_tut` (text)
- `course_level` (smallint) — minimum academic level a tutor must hold to apply, as a rank (`third_year`=3, `honours`=4, `masters`=5, `phd`=6); set from the organiser's Add/Edit Course form
- `venues` (text) — tutorial rooms, e.g. `"MSL004,005,006"`
- `Day_of_lab` (text)
- `lab_start_time`, `lab_end_time` (time)
- `lab_venues` (text)
- `budget` (numeric)
- `diagonal_count` (smallint, 2–26) — how many diagonals (student groups labelled A, B, C…) a large course is split into; null when it isn't split. Set from the organiser's Add/Edit Course form

#### `course_volunteers`

- A student's volunteering for a course, with the mark they self-reported.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK)
- `user_id` (uuid, required, FK → `users.id`)
- `course_id` (integer, required, FK → `courses.id`)
- `mark` (integer)
- `status` (text, required, default `pending`) — `pending`, `approved` or `rejected`
- `locked` (bool) — set once an organiser's decision is final: it locks an approval or a rejection. A locked row can't be reconsidered or withdrawn, so a locked rejection stops the student removing it to volunteer for the course again
- `rejection_reason` (text) — organiser's note written when the application is rejected
- `approval_reason` (text) — organiser's note written when the application is approved
- `diagonal` (text) — the diagonal (`A`–`Z`) an approved volunteer is placed in, when the course is split into diagonals; null = unassigned
- `created_at` (timestamptz, required, default now)

#### `tutor_subject_preference`

- A tutor's application to tutor a course, ranked by the mark they scored for it.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `course_id` (smallint, required, FK → `courses.id`)
- `status` (text) — `pending`, `approved` or `rejected`
- `Tutor_name` (text) — denormalised copy of the tutor's name
- `tutor_mark` (integer) — the mark the tutor scored for the course
- `Availability` (bool) — whether the tutor is free at the course's scheduled times
- `locked` (bool, required) — set once an organiser's decision is final: it locks an approval or a rejection. A locked row can't be reconsidered or withdrawn, so a locked rejection stops the tutor removing it to re-apply
- `rejection_reason` (text) — organiser's note written when the application is rejected
- `approval_reason` (text) — organiser's note written when the application is approved
- `diagonal` (text) — the diagonal (`A`–`Z`) an approved tutor is placed in, when the course is split into diagonals; null = unassigned

#### `allocation_overrides`

- Audit log written when an organiser approves an application that broke a rule — the course was already full, or the tutor would exceed their weekly hour cap.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `organiser_id` (uuid, required, FK → `users.id`) — the organiser who approved the override
- `tutor_id` (uuid, FK → `tutors.id`)
- `course_id` (smallint, FK → `courses.id`)
- `rule_overridden` (text, required) — `course_capacity` or `weekly_hour_cap`
- `reason` (text, required) — free-text justification supplied by the organiser
- `created_at` (timestamptz, required, default now)

#### `allocation_drafts`

- A saved draft of a proposed tutor allocation, which can be edited and later published.
- Read and written by the application API (`server/routes/allocationDrafts.js`): created by auto-allocate, renamed or pruned while open, then published or discarded.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `name` (text, required)
- `created_by` (uuid, required, FK → `users.id`)
- `status` (text, required)
- `created_at` (timestamptz, required, default now)
- `published_at` (timestamptz)

#### `allocation_draft_assignments`

- One tutor–course pairing inside a draft allocation.
- Read and written by the application API (`server/routes/allocationDrafts.js`): proposed by auto-allocate, removed when an organiser prunes an open draft, applied on publish.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `draft_id` (bigint, required, FK → `allocation_drafts.id`)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `course_id` (smallint, required, FK → `courses.id`)
- `explanation` (text)
- `locked` (bool)

#### `session_excusals`

- A tutor excusing themselves from one scheduled session of a course they are approved for.
- An approved student volunteer on the course is automatically assigned to cover it (`cover_user_id`), reminded the day before, and can hand it on if they can't make it.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `tutor_id` (uuid, required, FK → `tutors.id`)
- `course_id` (smallint, required, FK → `courses.id`)
- `session_date` (date, required)
- `session_type` (text) — `tutorial` or `lab`: which of the course's sessions the tutor is excused from; null on excusals recorded before this was tracked
- `reason` (text)
- `cover_user_id` (uuid, FK → `users.id`) — the student volunteer covering the session; null when no volunteer was free
- `cover_assigned_at` (timestamptz) — when the current cover was assigned
- `cover_reminded_at` (timestamptz) — when the day-before reminder went out, so it's only sent once
- `cover_declined_by` (uuid[], required, default `{}`) — volunteers who said they can't make it, so they aren't picked again
- `swap_to_user_id` (uuid, FK → `users.id`) — another volunteer the cover has asked to take the session over; the cover only moves once they accept. Null = no pending request
- `swap_requested_at` (timestamptz) — when that swap was asked for
- `created_at` (timestamptz, required, default now)

#### `session_swaps`

- A request to move one session's tutoring duty from one tutor to another.
- Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `course_id` (smallint, required, FK → `courses.id`)
- `session_date` (date, required)
- `from_tutor_id` (uuid, required, FK → `tutors.id`) — the tutor giving up the session
- `to_tutor_id` (uuid, required, FK → `tutors.id`) — the tutor taking it over
- `status` (text, required)
- `requested_at` (timestamptz, required)
- `reviewed_at` (timestamptz)

#### `tutor_busy_times`

- The classes on a user's calendar (added manually or imported from a timetable PDF), each recurring weekly. This is the only copy — the calendar loads them from here and keeps nothing in the browser — and the organiser board reads them for clash checks when assigning courses.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `tutor_id` (uuid, required, FK → `users.id`) — despite the name, any calendar user: student volunteers keep classes here too
- `title` (text) — e.g. the class name
- `day_of_week` (smallint, required, 0 = Sunday through 6 = Saturday)
- `start_time`, `end_time` (time, required)
- `first_date`, `end_date` (date) — the block's active range
- `venue` (text)
- `exceptions` (jsonb, required, default `[]`) — per-day changes to the recurring class, at most one per date: `{ date, type: "cancelled" }` or `{ date, type: "modified", overrides: { title?, startTime?, endTime?, venue? } }`
- `source` (text, required)
- `created_at` (timestamptz, required, default now)

#### `hour_entries`

- One row per work session a tutor logs; the raw material that weekly timesheets are built from.
- **Primary key**: `id`
- **Fields**:
- `id` (uuid, PK)
- `user_id` (uuid, required, FK → `users.id`)
- `course_id` (integer, FK → `courses.id`) — the course the hours were worked on; null for unlinked entries, which are excluded from the budget report
- `date` (date, required)
- `hours` (numeric, required)
- `start_time`, `end_time` (time)
- `task_type` (text, required, default `Tutoring`)
- `subject` (text)
- `notes` (text)
- `created_at` (timestamptz, required, default now)
- `updated_at` (timestamptz)
- `verification_status` (text, required, default `pending`) — the organiser's attendance-verification call on the logged session: `pending`, `verified` or `flagged`. Rows that predate the feature backfill to `pending`, and a structural edit by the entry's owner resets a decided entry back to `pending`
- `verified_by` (uuid, FK → `users.id`) — the organiser who made the call; null while pending
- `verified_at` (timestamptz)
- `verification_note` (text) — the organiser's explanation when they flag a logged session (required); verifying is a one-click call and writes no note

#### `timesheets`

- A tutor's monthly submission of logged hours, for organiser sign-off. `entries_snapshot` freezes the hour entries at submission time so later edits can't retroactively change an approved month.
- **Composite primary key**: `(user_id, week_start)`
- **Fields**:
- `user_id` (uuid, required, FK → `users.id`)
- `week_start` (date, required) — the first day of the submitted month. (The column name predates the switch from weekly to monthly periods — no schema migration was done, it just stores a month start now.)
- `status` (text, required, default `pending`) — `pending`, `approved` or `rejected`
- `submitted_at` (timestamptz, required, default now)
- `reviewed_at` (timestamptz)
- `reviewer_note` (text)
- `total_hours` (numeric)
- `entries_snapshot` (jsonb, required)

#### `timesheet_disputes`

- A dispute raised against a reviewed (approved or rejected) timesheet. Read and written via `/api/timesheet-disputes` — a tutor raises one against their own reviewed timesheet, an organiser resolves it.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `timesheet_user_id` (uuid, required, FK → `timesheets.user_id`)
- `timesheet_week_start` (date, required, FK → `timesheets.week_start`)
- `raised_by` (uuid, required, FK → `users.id`)
- `message` (text, required)
- `resolved` (bool, required)
- `created_at` (timestamptz, required, default now)

#### `academic_terms`

- University terms and recess periods, for term-aware calendar logic. Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `term_name` (text, required)
- `start_date`, `end_date` (date, required)
- `is_recess` (bool, required)

#### `notifications`

- Per-user notification feed. Written by several routes (application and volunteer decisions, timesheet statuses, session changes, cover assignments and swaps) via `server/routes/notificationHelpers.js`, and read by the bell icon's polling via `GET /api/notifications`. A subset of these types also sends an email copy to the address on the user's `users` row — see [Notification emails](./external-services.mdx#resend--notification-emails). This table is the source of truth either way: no email state is stored here, so a sent email can't be queried and a dropped one leaves no trace beyond a Worker log line.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `user_id` (uuid, required, FK → `users.id`)
- `type` (text, required)
- `message` (text, required)
- `related_entity` (text) — the kind of record the notification points at
- `related_id` (text)
- `read` (bool, required, default false)
- `created_at` (timestamptz, required, default now)

#### `audit_log`

- Generic audit trail: a before/after snapshot of any edited entity, recorded with the acting user.
- Not yet read or written by the application API — managed directly in Supabase.
- **Primary key**: `id`
- **Fields**:
- `id` (bigint, PK)
- `entity_type` (text, required) — the kind of record that changed
- `entity_id` (text, required)
- `action` (text, required)
- `actor_id` (uuid, FK → `users.id`) — the user who made the change
- `before`, `after` (jsonb) — snapshots of the record before and after
- `created_at` (timestamptz, required, default now)

## 2. Deployment

The database is a Supabase project: PostgreSQL for storage plus Supabase Auth for account management. The application server connects through `server/supabaseClient.js` (`@supabase/supabase-js`), configured with the `SUPABASE_URL` and `SUPABASE_ANON_KEY` environment variables.

- **Local development** — the Express server (`npm start`) reads them from `.env`.
- **Production** — the same app is deployed as a Cloudflare Worker (see `wrangler.toml` in the repository root).

Row Level Security is currently disabled on all tables, so the anon key can read and write every table; authorisation is enforced in the route handlers instead of the database.
