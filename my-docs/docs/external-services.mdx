# External Services

Every third-party service and CDN this app actually talks to: why it was chosen and how the integration actually works.

## Overview

Five external services are in active use — one database/auth/storage backend, one indirect OAuth provider, one AI API, and two CDN-hosted asset loads (which serve as that AI API's fallback). Nothing else in the app makes an outbound call to a third party: no payment processor, no email/SMS provider, no analytics/tracking script. The timetable reader's back-and-forth — LLM-only, then OCR-only, now both — is summarised in [Timetable parsing: a brief history](#timetable-parsing-a-brief-history) below.

## Supabase — database + auth

The app's only backend-as-a-service dependency, and the one everything else is built around. Full env-var/config detail is in [Backend](./backend.mdx); this section covers the rationale and mechanics.

### Why it's suitable

- **One product instead of three.** A managed Postgres database, a REST API in front of it, and a full auth system (email/password + OAuth) ship as one service — this is a small team building a full-stack app on a deadline, not standing up its own database server, writing its own JWT/session logic, or running its own OAuth flow.
- **A real relational database, not a document store bolted onto a BaaS.** The domain (tutors, courses, applications, timesheets, approvals with foreign keys between all of them) is inherently relational — Postgres's constraints and joins fit it directly, rather than working around a NoSQL model.
- **A generous free tier**, appropriate for a student project with no production budget.
- **One SDK, two environments.** `@supabase/supabase-js` works identically in Node (server-side) and in a plain `<script>` tag in the browser (client-side), which matters here since the frontend has no bundler — see `public/html/google-callback.html`, where it's loaded straight from jsdelivr with no build step.

### How it works

- The client is instantiated with `createClient(SUPABASE_URL, SUPABASE_ANON_KEY)` — **four separate times**, all pointed at the same project:
  - `app.js:17-27` — server-side client, attached to every request as `req.supabase`
  - `server/supabaseClient.js` — a second server-side client, imported by everything under `server/routes/*`
  - `routes/auth.js:405-417` — a third, built per-request with the _caller's_ access token instead of the anon key, specifically to verify Google sign-ins server-side
  - `public/html/google-callback.html` — a client-side instance, loaded from `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2`, with the URL/anon key inline in the HTML
- Every `server/routes/*.js` file talks to Postgres through the JS query builder (`supabase.from("table").select()/.insert()/.update()/.delete()`, with `.eq()`/`.neq()`/`.in()`/`.order()`/`.single()` etc.) — this compiles down to calls against Supabase's auto-generated PostgREST API, so the app never writes raw SQL.
- Auth (`routes/auth.js`) uses Supabase's own user table and session tokens for email/password sign-up and login — the app doesn't store or hash passwords itself.
- `server/routes/transcripts.js` also drives this client's **Storage** API — the private `transcripts` bucket described next — through the same SDK and key as everything else.
- **Caveat, not a strength:** Row Level Security is currently disabled on every table (flagged as an open item in [Backend](./backend.mdx#deployment)), so the suitability of "PostgREST auto-generates a REST API" cuts both ways — it's convenient, but it also means the anon key currently grants direct read/write to everything unless RLS gets turned back on.

### Applicant transcripts (Supabase Storage)

Tutor and volunteer applications each require a transcript on file, which the organiser reviews from the course boards. Those files can't be database rows (they're binary, up to 5 MB each) and can't live on the server's disk — production runs on Cloudflare Workers, which has no persistent filesystem — so they go to Supabase Storage: no extra service to provision, and the same SDK/credentials already in use.

How it works:

- **Private bucket, one folder per user.** Files are stored at `<userId>/transcript.<pdf|png|jpg>` in a private `transcripts` bucket. `userId` is the Supabase auth user id, which all roles share (see `routes/auth.js`), so one layout serves both tutor and volunteer applications.
- **Uploads are raw-body POSTs** (`POST /api/transcripts/:userId`, `express.raw`, 5 MB limit), and the bytes' magic number is checked against the declared content type — the client sets that header, so it isn't trusted on its own. PNG/JPEG are accepted alongside PDF so a phone photo of a printed transcript works too.
- **Viewing goes through short-lived signed URLs.** `GET /api/transcripts/:userId/signed-url` asks Storage for a URL valid for 5 minutes; `board.js` opens it in a new tab when an organiser clicks a row's Transcript button (and shows a toast when nothing has been uploaded). The bucket itself is never public.
- **Applications are gated on it.** `POST /api/tutor-applications` and `POST /api/course-volunteers` refuse with `403` until a transcript is on record (`hasTranscript()` in `server/routes/transcriptStorage.js`).
- **Setup is manual, once per Supabase project** — create the private `transcripts` bucket and a policy for the anon role (step 3 in [Getting Started](./getting-started.mdx)). Until that's done, an upload answers `503` with a message saying so (status checks just look empty), rather than failing opaquely.
- **Profile timetables share the bucket.** Tutors and volunteers can keep their class-timetable PDF on their profile page (`server/routes/profileTimetable.js`, mounted at `/api/profile/:userId/timetable`: `GET` status, `POST` upload/replace, `GET …/signed-url`, `DELETE`). It's stored at `<userId>/timetable.pdf` in the same `transcripts` bucket, so the existing bucket and anon policy cover it with no extra setup, and `listTranscripts()` only matches `transcript.*`, so a saved timetable never counts as a transcript.
- **Timesheet claim PDFs share the bucket too.** When a tutor submits a month, their browser renders the claim form itself (html2canvas + jsPDF — production runs on Cloudflare Workers, with no server-side browser to do it) and uploads it via `POST /api/timesheets/:userId/:weekStart/pdf` to `<userId>/timesheets/<monthStart>.pdf` in the same bucket. Organisers open it from the review queue's PDF button, which fetches a 5-minute signed URL (`GET …/pdf-url`); months filed before this feature simply answer `404` and the button points at the Details view instead.

## Google OAuth — via Supabase, not a direct integration

### Why it's suitable

- Wits students and staff already have Google-backed accounts, so "Continue with Google" removes a step (choosing yet another password) for the exact audience this app is built for.
- Delegating the actual OAuth2 dance to Supabase avoids implementing the authorization-code flow — redirect, state/PKCE handling, code-for-token exchange, verifying Google's signed tokens — by hand. That flow is easy to get subtly wrong in ways that are security bugs, not just UX bugs, so reusing Supabase's already-audited implementation is the safer choice for a small team.
- No separate Google Cloud credential has to be managed in this repo's own config — it lives in the Supabase project dashboard instead, one fewer secret to keep track of here.

### How it works

There's no direct call to `accounts.google.com` or any `googleapis.com` endpoint anywhere in this codebase, and no Google Identity Services script — the whole flow is proxied through Supabase Auth:

1. `public/js/auth.js` — the "Continue with Google" button just navigates the browser to `/api/auth/google` (an internal route, not Google).
2. `routes/auth.js` (`GET /api/auth/google`) — calls `req.supabase.auth.signInWithOAuth({ provider: "google" })`. Supabase returns a Google consent-screen URL; the server redirects the browser there.
3. The user approves on Google's own page. Google redirects back to a Supabase-managed callback, which Supabase turns into an authorization code and hands off to this app's own `public/html/google-callback.html`.
4. `google-callback.html` calls `supabaseClient.auth.exchangeCodeForSession(code)` — this is the actual code-for-session exchange, but it's a call _to Supabase_, not to Google; Supabase holds the Google client secret and does the real token exchange behind the scenes.
5. `routes/auth.js` (`POST /api/auth/google/register`) then verifies the resulting Supabase access token via `authenticatedSupabase.auth.getUser(accessToken)` before creating this app's own `users`/`organisers`/etc. row for a first-time Google sign-in.

## Google Fonts

### Why it's suitable

The frontend has no build step and no bundler (see [Frontend](./frontend.mdx)), so self-hosting font files would mean manually managing `@font-face` declarations and static assets for four typefaces. Google Fonts' CDN does that for free, with far better cache-hit odds across visitors' browsers than a self-hosted file would get, and no license/hosting management on the app's side.

### How it works

Each page that needs custom typography (most of `public/html/`) carries a `<link rel="preconnect">` (opens the connection early) plus a `<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=...">` for Fraunces, Space Grotesk, Inter, and IBM Plex Mono. That stylesheet response is itself just `@font-face` rules pointing at `.woff2` files on `fonts.gstatic.com`; the browser fetches whichever weights/styles the page's CSS actually uses. No credential, no API call from the app's own code — it's a static asset fetch.

## jsdelivr CDN — pdf.js and Tesseract.js

### Why it's suitable

This pipeline is the on-device fallback for timetable parsing, kept alongside the primary AI reader ([Google Gemini](#google-gemini-api--reading-timetable-pdfs) below) because it covers what the AI route can't — no API key in a given environment, quota exhausted, or Google unreachable:

- **The source PDFs leave no other option than OCR or a multimodal model.** Wits's exported "My Class Schedule" PDFs are a print-to-PDF of a rendered grid — every character is an outlined shape (a path), not a `Tj` text-drawing operator, so there's no embedded text layer to read directly. Rendering to a bitmap and running OCR is the only way to recover the text without an LLM.
- **Running it client-side avoids paying for or depending on a hosted API** — no per-request cost, no API key to provision or leak, and the feature keeps working even when the hosted AI vendor's quota runs out or the service goes down.
- **Privacy**: on this path the PDF (which contains a student's real class schedule) never leaves the browser — worth stating explicitly, since the primary AI path does upload it to our server and on to Google.
- **Both libraries are the standard, actively-maintained choice for their job**, not a niche pick: pdf.js is Mozilla's own PDF renderer (the same engine Firefox uses to display PDFs in-tab), and Tesseract.js is a WebAssembly port of the long-established Tesseract OCR engine, built specifically to run OCR inside a browser tab.
- **Loading from jsdelivr instead of bundling them** keeps the no-build-step frontend simple — one `import()` statement instead of a bundler config — while jsdelivr's CDN caching means most visitors already have these exact pinned versions cached from some other site.

### How it works

The whole pipeline lives in `public/js/timetable-parser.js`, invoked when a user uploads a timetable PDF on the calendar page and the server-side AI reader turns out to be unavailable:

1. **Lazy load.** `loadPdfjs()` / `loadTesseract()` dynamically `import()` the libraries from jsdelivr only when a PDF is actually being parsed — pages that never touch this feature never pay for the download.
   ```js
   const PDFJS_URL =
     "https://cdn.jsdelivr.net/npm/pdfjs-dist@6.3.289/build/pdf.min.mjs";
   const TESSERACT_URL =
     "https://cdn.jsdelivr.net/npm/tesseract.js@7.0.0/dist/tesseract.esm.min.js";
   ```
2. **Render.** The uploaded `File` is read into a `Uint8Array` and handed to `pdfjsLib.getDocument({ data })`. For each page, `renderPageToCanvas()` draws it onto an in-memory `<canvas>` at 3x scale (`RENDER_SCALE = 3`) — upscaling measurably improves OCR accuracy on small grid text.
3. **OCR.** A `Tesseract.createWorker("eng")` worker is created once and reused across every page. `extractWords()` calls `worker.recognize(canvas, {}, { blocks: true, text: true })`, which returns each recognized word with its bounding box (`x0/y0/x1/y1`), not just a flat text blob.
4. **Reconstruct the grid.** `parseGridWords()` uses those word positions — not the text alone — to work out which words share a row/column, i.e. to rebuild the timetable's grid structure (day columns, time rows, class blocks) purely from geometry. `mergeEntries()` then folds adjacent OCR'd fragments of the same class back into single entries.
5. **Output.** The function returns a plain array of `{ title, dayName, dayOfWeek, startTime, endTime, venue }` objects — the rest of the app (busy-times import) treats this exactly like any other structured input, with no awareness that OCR was involved.
6. The Tesseract worker is explicitly `terminate()`d in a `finally` block once every page is processed, freeing the WASM worker thread.
7. **Reached only as a fallback.** `parseTimetablePdf()` tries the AI route first; this pipeline runs when that attempt fails with `aiUnavailable` set (a 5xx from our route or a network error — see the Gemini section). A 4xx rejection such as "wrong file type" is surfaced to the user as-is instead, because OCR would only repeat the same failure.

## Google Gemini API — reading timetable PDFs

### Why it's suitable

- **PDF-native multimodal input.** `generateContent` accepts the PDF file itself (base64 inline data), not just pre-extracted text — so it can read the outlined-shape exports that have no text layer at all, and it copes with whatever layout a student's own timetable export happens to use, not just the one grid the in-browser OCR was tuned against.
- **Structured output instead of free text.** The request sets `responseJsonSchema`, so the model must answer in the exact `{ classes: [{ courseCode, courseName, dayName, startTime, endTime, venue }] }` shape the calendar import needs — no brittle parsing of prose.
- **A free tier covers this project's volume** (one small request per uploaded PDF), and there's no new dependency: the call is a single `fetch` POST, so nothing extra ships to the Workers runtime.
- **The key stays server-side.** `GEMINI_API_KEY` is read by the route, not by the browser — the client only ever talks to our own `/api/timetable/parse`.

### How it works

All of it lives in `server/routes/timetable.js`, mounted at `/api/timetable`:

1. **Upload.** `public/js/timetable-parser.js` POSTs the raw PDF bytes (`Content-Type: application/pdf`) — not multipart — so the route reads them with `express.raw` (15 MB limit, comfortably inside Gemini's 20 MB inline-request cap after base64 inflation).
2. **Validate.** Content type must be `application/pdf`, the body must contain the `%PDF-` magic bytes within its first 1024 bytes, and `GEMINI_API_KEY` must be configured — otherwise `400`/`503` before any API call is made.
3. **Ask Gemini.** One `fetch` per model to `https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, authenticated with an `x-goog-api-key` header. The body carries the PDF as `inlineData` plus the extraction prompt and the JSON schema. A 90-second `AbortController` deadline bounds the whole request, and each individual attempt is capped at 20 seconds so a hung model fails over instead of eating that budget. Rather than depending on one model staying healthy, the route walks a probe-verified candidate list (`gemini-3.5-flash-lite`, `gemini-3.1-flash-lite`, `gemini-3-flash-preview`, `gemini-3.7-flash`): transient `5xx` responses are retried twice per model with a short backoff, and a capacity answer (`404` retired / `429` quota / `503` high demand / `504` timeout) moves it on to the next candidate. `GEMINI_MODEL` pins a single model and skips the failover.
4. **Normalise.** Even though the schema pins the model's output shape, the route still validates every row (day name against the canonical list, `HH:MM` times, at least one of code/name present) and drops anything unusable rather than trusting the model blindly. Rows are sorted by day and start time.
5. **Respond.** `{ classes: [...] }` on success. Failures are split deliberately: `400`/`413` mean the _request_ was bad (surfaced to the user, no fallback), while `502`/`503` mean the _reader_ was unavailable — the client marks the AI path unavailable and switches to the in-browser OCR pipeline (previous section).

:::info Setup

- **Local:** `GEMINI_API_KEY` in `.env` (see [Getting Started](./getting-started.mdx)) — plus an optional `GEMINI_MODEL` override.
- **Production (Cloudflare Worker):** `deploy.yml` syncs the key from a **Gitea repo secret** (`GEMINI_API_KEY`) into the production Worker on every main deploy — `.env` isn't read there ([Backend](./backend.mdx) explains the split). To rotate the key, update the repo secret. Don't `wrangler secret put` from a developer laptop: the local wrangler login is a different Cloudflare account that owns a same-named `tutorx` Worker, so the key lands on the wrong one — exactly how the live route ended up answering `503` while local worked.
- **No key?** The route answers `503` and the calendar page quietly reads PDFs on-device instead — the feature never hard-fails just because AI parsing is unconfigured.
- **Free-tier limits apply.** The free plan caps each model at **20 requests/day** (daily, not per-minute), so repeated manual testing can exhaust it; a `429 RESOURCE_EXHAUSTED` that persists for hours is oddly reassuring — it proves the key is valid (invalid keys get `400`). The route retries transient `5xx` twice per model, a `429` never retries the same model but fails over to the next candidate, and if every candidate is unavailable the client still reads the PDF on-device — a busy day degrades gracefully, it doesn't break the feature.
  :::

## Timetable parsing: a brief history

The feature has changed shape twice and then needed one production fix; this page has documented each state:

1. **Server-side LLM only** — the original implementation (`server/timetableRoutes.js` + `server/geminiClient.js`, first Anthropic then Gemini, on the `feature/external_api` branch) called the model for everything and had no client-side reader at all.
2. **Client-side OCR only** — the rewrite that replaced it ran pdf.js + Tesseract.js entirely in the browser, with no server route and no API key anywhere. (This is the pipeline the fallback above still uses.)
3. **Hybrid** — Gemini is back as the primary reader via the same route, and the OCR pipeline is kept as the automatic fallback. `GEMINI_API_KEY` is read by the code again, so treat it as live config, not a leftover.
4. **Production fix (current)** — the restored route worked locally but not on the live site: the deployed Worker had no `GEMINI_API_KEY` secret, so it answered `503` and the calendar page silently fell back to OCR, which surfaced to users as "No classes could be recognised in this PDF". Two traps made the diagnosis slow: a same-named `tutorx` Worker in a second Cloudflare account absorbed a manual `wrangler secret put` (the laptop's wrangler login belongs to that other account), and the free tier's per-model **daily** quota made the then-default model look permanently dead. Fixed by having `deploy.yml` push the key into the production Worker from a Gitea repo secret on every deploy, and by the probe-verified multi-model failover cascade described above. Verified working end-to-end against production.

## Everything else

- All `fetch()` calls in `public/js/**` (storage.js, board.js, tutors.js, dashboard.js, etc.) hit this app's own `/api/...` routes — same-origin, not an external service.
- No `axios` or `XMLHttpRequest` anywhere in the repo.
- `package.json` dependencies are limited to `@supabase/supabase-js`, `cors`, `dotenv`, `express` (+ dev deps `jest`, `jsdom`, `prettier`, `supertest`, `wrangler`) — no payment, email/SMS, analytics, or AI SDK among them: the Gemini call is a plain `fetch`.
