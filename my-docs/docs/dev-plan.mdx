# Dev Plan

System design, tech stack rationale, and feature roadmap for the Tutor Management System — COMS3011A Project 1.

**Design reference:** [Figma — web app mockup](https://www.figma.com/make/QS99jxkDOBQ2Hud25McAS5/Webapp-Mockup?t=IXSgvEikzq7Eoq7H-20&fullscreen=1) — the intended look and feel for the whole web app.

This page reflects the build as of late Sprint 3 (September 2026).

## Problem statement

The School of Computer Science and Applied Mathematics needs a better way to manage tutors. The platform must let an **organiser** assign available tutors to courses based on the tutor's mark in the course, their availability against their own timetable, and hours already worked per week. It also needs to let **students volunteer** for overflow tutoring work, let **tutors** sign and submit timesheets and excuse themselves from sessions, and generally support the admin work around running a tutoring programme.

## Roles

- **volunteer** (renamed from "student"), **tutor**, **organiser** and **super_organiser** — the four roles today.
- **educator** — dropped. It was planned as a fourth role, but a dedicated educator interface would have near-duplicated the organiser's. Instead, lecturers / professors / teaching assistants register as organisers, each restricted to their own course.
- **organiser** — registration asks which course the organiser wants and files an `organiser_requests` row for it. Until the super-organiser approves, sign-in is blocked; once approved, the organiser's board shows only that course. Organisers registered before requests existed keep full access.
- **super-organiser** (admin) — one account, promoted by hand in Supabase (`users.role = 'super_organiser'` — see [Getting Started](/docs/getting-started#4-set-up-organiser-access-one-off)). It sees every course and reviews organiser requests on its own page.

## How this meets the course's key requirements

| Requirement                       | How this project meets it                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Non-monolithic front-end/back-end | Front-end is static HTML/CSS/vanilla JS (`public/`); back-end is a separate Express API (`app.js` + `routes/`, `server/routes/`). No framework merges the two.                                                                                                                                                                                                                                                                                     |
| Hand-Written API                  | Every endpoint under `/api/*` is a hand-written Express route (see [API design](#api-design) below). The frontend never talks to Supabase's auto-generated REST API directly — it always goes through our own routes, which then use `@supabase/supabase-js` internally as a database/auth client.                                                                                                                                                 |
| Authentication & Security         | Sign up / sign in via **Supabase Auth** (`routes/auth.js`) — email + password (`signUp` / `signInWithPassword`) and Google OAuth (`/api/auth/google`, `/api/auth/google/register`). An established library, not a hand-rolled auth system.                                                                                                                                                                                                         |
| Integration (external API)        | Timetable PDF import is hybrid: `POST /api/timetable/parse` sends the PDF to the **Gemini API** server-side (`server/routes/timetable.js`) as the primary path; if that fails (or no key is configured), the browser falls back to **pdf.js + Tesseract.js** OCR (`public/js/timetable-import.js`, `timetable-parser.js`). Wits timetable PDFs have no text layer (outlined shapes, not real text), so one of the two extractors is always needed. |
| CI/CD                             | Gitea Actions (`.gitea/workflows/`): `format.yml` (Prettier check) and `test.yml` (Jest suite) on every push; `deploy.yml` deploys the app to Cloudflare Workers on push to `main`; `docs-deploy.yml` deploys this documentation site on push to `main`. The `.gitlab-ci.yml` in the repo root is a leftover from before we realised the server runs Gitea, not GitLab — it never executes and can be ignored.                                     |
| Documentation Website             | This site (Docusaurus, `my-docs/`), deployed via Cloudflare Pages.                                                                                                                                                                                                                                                                                                                                                                                 |
| Responsiveness & Accessibility    | Layouts reflow at the 720px and mobile breakpoints through the shared stylesheet, and boards and guided tours are keyboard-navigable (see [Frontend](./frontend.mdx)).                                                                                                                                                                                                                                                                             |

## System architecture

```
Browser (public/html + public/js)
        │  fetch() to /api/*
        │  timetable PDF → Gemini (primary) or in-browser pdf.js + Tesseract.js OCR (fallback)
        ▼
Express app (app.js)
        │
        ├── routes/auth.js ─────────────► Supabase Auth (email + Google OAuth)
        ├── server/routes/courses.js ───► Supabase Postgres (courses, diagonals)
        ├── server/routes/tutors.js ────► Supabase Postgres (tutors, workload, rates)
        ├── server/routes/hourEntries.js ─► Supabase Postgres (logged hours, budget report)
        ├── server/routes/courseVolunteers.js + tutorApplications.js ─► Supabase Postgres
        ├── server/routes/timesheets.js + timesheetDisputes.js ─► Supabase Postgres (monthly sign-off, payroll, disputes)
        ├── server/routes/sessionExcusals.js ─► Supabase Postgres (excusals; sessionCover.js auto-assigns covers/swaps)
        ├── server/routes/notifications.js ─► Supabase Postgres (in-app notifications)
        ├── server/routes/timetable.js ─► Gemini API (timetable PDF → class blocks)
        └── server/routes/publicApi.js ─► read-only public API (/api/v1)
```

`app.js` is the single source of truth for the Express app — both entry points (`server.js` for a normal Node process, `worker.js` for a Cloudflare Worker via Wrangler) load the same `app.js` and just differ in how static assets are served and how the process listens.

## Tech stack

| Layer                | Choice                                                                                                                                                   | Why                                                                                                                                                                                                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Backend runtime      | Node.js + Express 5                                                                                                                                      | Small, well-understood, easy to hand-write REST routes on — satisfies the Hand-Written API requirement directly.                                                                                                                                                               |
| Database + Auth      | Supabase (Postgres + Supabase Auth)                                                                                                                      | Managed Postgres without hosting our own DB; Supabase Auth satisfies "may not write your own authentication system." We only ever call it from our own server routes, never expose it directly to the client.                                                                  |
| External integration | Gemini API (server-side) + pdf.js/Tesseract.js fallback (client-side, CDN)                                                                               | Timetable PDF exports have no embedded text layer (outlined shapes, not real text), so extraction needs an LLM or OCR. Gemini gives the best results; the in-browser OCR fallback keeps the feature working without an API key, so there's no hard dependency on the paid API. |
| Frontend             | Vanilla HTML/CSS/JS (`public/`)                                                                                                                          | No build step, no framework — keeps the front-end genuinely separate from the back-end (see non-monolithic requirement) and easy for every team member to touch regardless of framework experience.                                                                            |
| Deployment target(s) | Cloudflare Workers (`worker.js` via Wrangler), deployed automatically by `deploy.yml` on push to `main`. `server.js` still exists for local `npm start`. | Satisfies the deployment requirement; auto-deploys on every meaningful update per the team's agreed build-release cycle.                                                                                                                                                       |
| Docs site            | Docusaurus, deployed to Cloudflare Pages                                                                                                                 | Markdown-based, satisfies the course's documentation-site requirement, deploys as a static site with no account-gated platform.                                                                                                                                                |
| CI                   | Gitea Actions (`.gitea/workflows/`)                                                                                                                      | Self-hosted Gitea, not GitLab — format-check and test workflows on every push, app-deploy and docs-deploy on `main`.                                                                                                                                                           |

## API design

All endpoints are mounted under `/api` by `app.js`. The full data model behind them is documented on the [Database Schema](/docs/Database-Schema) page.

### Auth

| Method & path                                            | Purpose                                                                                                                                                                                                                           |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/register`                                | Create a Supabase Auth user + row in `users` (and role-specific table: `students` for volunteers, `tutors`, or `organisers`). Self-signup offers volunteer/tutor/organiser — the educator role was dropped (see [Roles](#roles)). |
| `GET /api/auth/google`, `POST /api/auth/google/register` | Google OAuth sign-in / registration.                                                                                                                                                                                              |
| `POST /api/auth/login`                                   | Authenticate via Supabase, return session + `{ id, email, name, role }`.                                                                                                                                                          |

### Courses and allocation

| Method & path                                                                                                                                           | Purpose                                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET/POST /api/courses`, `PUT /api/courses/:id`, `DELETE /api/courses/:id`, `PATCH /api/courses/:id/tutors-assigned`                                    | Course records an organiser manages (with venue-clash validation).                                                                                                                                                              |
| `GET /api/courses/:courseId/diagonals`, `POST .../diagonals/split`, `PATCH .../diagonals/members`                                                       | Split a large course's tutors and volunteers into diagonals (A, B, C…) and move members between them.                                                                                                                           |
| `GET /api/tutors`, `GET /api/tutors/:id`, `POST /api/tutors`, `PUT /api/tutors/:id`, `DELETE /api/tutors/:id`                                           | Tutor records.                                                                                                                                                                                                                  |
| `GET /api/tutors/workload`                                                                                                                              | Each tutor's assigned hours vs their weekly cap, for the workload spread view.                                                                                                                                                  |
| `GET /api/tutors/rates`                                                                                                                                 | The configured hourly rates per academic level.                                                                                                                                                                                 |
| `PUT /api/tutors/bulk`                                                                                                                                  | Update a field (weekly hour cap) across all tutors at once.                                                                                                                                                                     |
| `POST /api/tutors/bulk-rates`                                                                                                                           | Set hourly rates per academic level across all matching tutors.                                                                                                                                                                 |
| `GET /api/tutors/:id/busy-times`                                                                                                                        | A user's calendar classes (tutor or volunteer), with their per-day exceptions.                                                                                                                                                  |
| `POST /api/tutors/:id/busy-times`                                                                                                                       | Add one or more classes (`{ classes: [...] }`), manually or from a timetable import.                                                                                                                                            |
| `PATCH /api/tutors/:id/busy-times/:busyTimeId`                                                                                                          | Change some fields of one class, including its per-day exceptions.                                                                                                                                                              |
| `DELETE /api/tutors/:id/busy-times/:busyTimeId`                                                                                                         | Remove one class.                                                                                                                                                                                                               |
| `DELETE /api/tutors/:id/busy-times`                                                                                                                     | Remove all of a user's classes.                                                                                                                                                                                                 |
| `GET /api/tutors/:id/assignment-check`                                                                                                                  | Timetable clashes and projected weekly hours if the tutor were assigned to a course.                                                                                                                                            |
| `GET/POST /api/tutor-applications`, `PATCH /api/tutor-applications/:id`, `PATCH /api/tutor-applications/:id/lock`, `DELETE /api/tutor-applications/:id` | Tutors applying to tutor a specific course; organiser approval/rejection (with override audit logging); the lock makes an approval or rejection permanent — a locked rejection can't be withdrawn, so the tutor can't re-apply. |
| `GET /api/tutor-applications/obvious-fill`                                                                                                              | Pending applications that can be approved with no judgment call.                                                                                                                                                                |
| `POST /api/tutor-applications/bulk-approve`                                                                                                             | Approve several applications in one action.                                                                                                                                                                                     |

### Volunteering and sessions

| Method & path                                                                                                                                                      | Purpose                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET/POST /api/course-volunteers`, `DELETE /api/course-volunteers`                                                                                                 | Students volunteering for overflow course work (with mark threshold check).                                                                                                                                    |
| `GET /api/course-volunteers/counts`                                                                                                                                | Number of volunteers per course, for the course list view.                                                                                                                                                     |
| `PATCH /api/course-volunteers/:id`                                                                                                                                 | Organiser approves/rejects/resets a volunteer; `PATCH /api/course-volunteers/:id/lock` makes an approval or rejection permanent — a locked rejection can't be withdrawn, so the student can't volunteer again. |
| `GET/POST /api/session-excusals`, `DELETE /api/session-excusals/:id`                                                                                               | A tutor excusing themselves from one scheduled session of an assigned course.                                                                                                                                  |
| `POST /api/session-excusals/:id/find-cover`, `/:id/decline-cover`, `GET /:id/swap-candidates`, `POST /:id/swap-request`, `/:id/swap-withdraw`, `/:id/swap-respond` | Auto-pick a volunteer cover for an excused session, decline a cover, and manage volunteer-to-volunteer swap requests.                                                                                          |

### Hours, timesheets and notifications

| Method & path                                                                                 | Purpose                                                                                                                                                                |
| --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET/POST /api/hour-entries`, `PUT /api/hour-entries/:id`, `DELETE /api/hour-entries/:id`     | Logged tutoring hours (tutor sessions and volunteer covers: only during the session + 10-minute grace window).                                                         |
| `GET /api/hour-entries/report`                                                                | Hours-budget report per course (only entries linked to a course).                                                                                                      |
| `GET /api/attendance-verification`, `PATCH /api/attendance-verification/:id`                  | Organiser verifies or flags logged session attendance; both sides are notified.                                                                                        |
| `GET/POST /api/timesheets`                                                                    | A tutor's monthly submissions; the organiser's review queue. A rejected month can be resubmitted once the tutor has fixed their logged hours.                          |
| `PATCH /api/timesheets/:userId/:weekStart`                                                    | Organiser approves/rejects a submitted month.                                                                                                                          |
| `POST /api/timesheets/:userId/:weekStart/pdf`                                                 | The tutor's browser uploads the month's claim PDF (raw `application/pdf` body, 15 MB limit, must start with `%PDF-`); refused with a 409 unless the month is rejected. |
| `GET /api/timesheets/:userId/:weekStart/pdf-url`                                              | 5-minute signed URL for the month's stored claim PDF (404 when none is on file).                                                                                       |
| `GET /api/timesheets/payroll-export`                                                          | CSV of every approved timesheet with tutor identity, rate and amount owed.                                                                                             |
| `GET /api/timesheets/due-reminder`                                                            | Timesheets due soon, surfaced by the notification bell.                                                                                                                |
| `GET/POST /api/timesheet-disputes`, `PATCH /api/timesheet-disputes/:id/resolve`               | A tutor disputes a reviewed timesheet; the organiser resolves it.                                                                                                      |
| `GET /api/notifications`, `PATCH /api/notifications/read-all`, `PATCH /api/notifications/:id` | In-app notification bell: session changes, cover requests/reminders, approvals.                                                                                        |

`POST /api/timetable/parse` turns a timetable PDF into class blocks via the Gemini API, with in-browser pdf.js + Tesseract.js OCR as the fallback (see [Integration](#how-this-meets-the-courses-key-requirements)). Also on `app.js`: `GET /api/test` (Supabase health check) and the read-only `/api/v1/*` public endpoints (see [Public API](/docs/public-api)).

## Roadmap

Grouped by the course's Basic / Intermediate / Advanced tiers, with the current state marked.

### Basic (in place)

- Sign up / sign in via email + password or Google OAuth (roles: volunteer — formerly "student" —, tutor, organiser)
- Organiser: create/edit courses, assign tutors (with timetable-clash and weekly-hours checks), split big courses into diagonals (A, B, C…)
- Tutor: log hours (session + 10-minute grace window), submit monthly timesheets, view calendar
- Tutor: excuse themselves from a session — a volunteer is auto-picked as cover (with swaps and reminders)
- Volunteer: sign up for overflow course work and cover excused sessions
- Tutor: apply to tutor a course (mark + availability check, organiser approval flow)
- Timetable import from a PDF (Gemini API primary, in-browser pdf.js + Tesseract.js OCR fallback)
- Timesheet disputes, payroll CSV export, hours-budget report, in-app notifications, read-only public API (`/api/v1`)

### Intermediate

- Automated testing — **done**: Jest suites for the server routes and client storage (`*.test.js`), run by `test.yml` on every push
- Database schema documentation — **done**: [Database Schema](/docs/Database-Schema) page (tables, columns, relationships, ERD)
- Bug tracker — **done**: tasks and bugs are tracked on the team's [Jira board](https://thedevden.atlassian.net/jira/core/projects/TMS/board) (project `TMS`)
- Per-course organiser restriction + **super-organiser** (admin) role — **done**: sign-up asks organisers for their course, the super-organiser approves each request on its own page, and organisers only see their approved course (see [Roles](#roles))
- Responsiveness/accessibility pass

### Advanced

- Deployment pipeline — **done**: `deploy.yml` ships every push to `main` to Cloudflare Workers automatically
- Performance pass
- Extended stakeholder feedback loop with the assigned client tutor

### Methodology

The team works in Scrum-style sprints aligned to the course milestones (Sprint _n_ = Milestone _n_), with sprint-planning meetings, 2–3 daily scrums per week, and a named Scrum Master / role split. All tasks, bugs and sprint work are tracked on the team's [Jira board](https://thedevden.atlassian.net/jira/core/projects/TMS/board) (project `TMS`), which serves as our Kanban board and issue tracker. Per-sprint meeting minutes are kept in this documentation site as additional process evidence, together with the user-feedback rounds — see the combined [Sprint Minutes & User Feedback](/docs/meeting-minutes) page.
