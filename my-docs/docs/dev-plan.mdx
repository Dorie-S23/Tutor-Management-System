# Dev Plan

System design, tech stack rationale, and feature roadmap for the Tutor Management System — COMS3011A Project 1.

:::info Living document
This reflects the build as of Milestone 2 (2026-09-15) plus the proposed roadmap for Sprints 3–4. The remaining **TODO** markers are scheduled work items, not unfinished writing.
:::

## Problem statement

The School of Computer Science and Applied Mathematics needs a better way to manage tutors. The platform must let an **organiser** assign available tutors to courses based on the tutor's mark in the course, their availability against their own timetable, and hours already worked per week. It also needs to let **students volunteer** for overflow tutoring work, let **tutors** sign and submit timesheets and excuse themselves from sessions, and generally support the admin work around running a tutoring programme.

## How this meets the course's key requirements

| Requirement                       | How this project meets it                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Non-monolithic front-end/back-end | Front-end is static HTML/CSS/vanilla JS (`public/`); back-end is a separate Express API (`app.js` + `routes/`, `server/routes/`). No framework merges the two.                                                                                                                                                                                                                                                         |
| Hand-Written API                  | Every endpoint under `/api/*` is a hand-written Express route (see [API design](#api-design) below). The frontend never talks to Supabase's auto-generated REST API directly — it always goes through our own routes, which then use `@supabase/supabase-js` internally as a database/auth client.                                                                                                                     |
| Authentication & Security         | Sign up / sign in via **Supabase Auth** (`routes/auth.js`) — email + password (`signUp` / `signInWithPassword`) and Google OAuth (`/api/auth/google`, `/api/auth/google/register`). An established library, not a hand-rolled auth system. **TODO:** self-service password reset and account deletion flows are not implemented yet — required by the brief, needs scheduling.                                         |
| Integration (external API)        | Timetable PDF import runs entirely in the browser (`public/js/timetable-import.js`, `public/js/timetable-parser.js`): **pdf.js** renders the uploaded PDF to a bitmap and **Tesseract.js** OCRs it into class blocks (day, time, venue) that seed the calendar. Wits timetable PDFs have no text layer (outlined shapes, not real text), so OCR is required. No server round-trip, no API key, no cost.                |
| CI/CD                             | Gitea Actions (`.gitea/workflows/`): `format.yml` (Prettier check) and `test.yml` (Jest suite) on every push; `deploy.yml` deploys the app to Cloudflare Workers on push to `main`; `docs-deploy.yml` deploys this documentation site on push to `main`. The `.gitlab-ci.yml` in the repo root is a leftover from before we realised the server runs Gitea, not GitLab — it never executes and can be ignored/removed. |
| Documentation Website             | This site (Docusaurus, `my-docs/`), deployed via Cloudflare Pages.                                                                                                                                                                                                                                                                                                                                                     |
| Responsiveness & Accessibility    | **TODO:** not yet audited — schedule the pass ahead of Milestone 3.                                                                                                                                                                                                                                                                                                                                                    |

## System architecture

```
Browser (public/html + public/js)
        │  fetch() to /api/*
        │  timetable PDF → pdf.js (render) + Tesseract.js (OCR), fully in-browser
        ▼
Express app (app.js)
        │
        ├── routes/auth.js ─────────────► Supabase Auth (email + Google OAuth)
        ├── server/routes/courses.js ───► Supabase Postgres (courses)
        ├── server/routes/tutors.js ────► Supabase Postgres (tutors, busy times, workload)
        ├── server/routes/hourEntries.js ─► Supabase Postgres (logged hours)
        ├── server/routes/courseVolunteers.js ─► Supabase Postgres
        ├── server/routes/tutorApplications.js ─► Supabase Postgres
        ├── server/routes/timesheets.js ─► Supabase Postgres (weekly sign-off)
        └── server/routes/sessionExcusals.js ─► Supabase Postgres
```

`app.js` is the single source of truth for the Express app — both entry points (`server.js` for a normal Node process, `worker.js` for a Cloudflare Worker via Wrangler) load the same `app.js` and just differ in how static assets are served and how the process listens.

## Tech stack

| Layer                | Choice                                                                                                                                                   | Why                                                                                                                                                                                                                                                                                                                                           |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend runtime      | Node.js + Express 5                                                                                                                                      | Small, well-understood, easy to hand-write REST routes on — satisfies the Hand-Written API requirement directly.                                                                                                                                                                                                                              |
| Database + Auth      | Supabase (Postgres + Supabase Auth)                                                                                                                      | Managed Postgres without hosting our own DB; Supabase Auth satisfies "may not write your own authentication system." We only ever call it from our own server routes, never expose it directly to the client.                                                                                                                                 |
| External integration | pdf.js + Tesseract.js (loaded client-side from a CDN)                                                                                                    | Timetable PDF exports have no embedded text layer (outlined shapes, not real text), so the browser renders the page to a bitmap and OCRs it — no server round-trip, no API key, no cost. Originally an LLM-based server route (Anthropic, then briefly Gemini); moved client-side after deciding not to depend on a paid/hosted API for this. |
| Frontend             | Vanilla HTML/CSS/JS (`public/`)                                                                                                                          | No build step, no framework — keeps the front-end genuinely separate from the back-end (see non-monolithic requirement) and easy for every team member to touch regardless of framework experience.                                                                                                                                           |
| Deployment target(s) | Cloudflare Workers (`worker.js` via Wrangler), deployed automatically by `deploy.yml` on push to `main`. `server.js` still exists for local `npm start`. | Satisfies the deployment requirement; auto-deploys on every meaningful update per the team's agreed build-release cycle.                                                                                                                                                                                                                      |
| Docs site            | Docusaurus, deployed to Cloudflare Pages                                                                                                                 | Markdown-based, satisfies the course's documentation-site requirement, deploys as a static site with no account-gated platform.                                                                                                                                                                                                               |
| CI                   | Gitea Actions (`.gitea/workflows/`)                                                                                                                      | Self-hosted Gitea, not GitLab — format-check and test workflows on every push, app-deploy and docs-deploy on `main`.                                                                                                                                                                                                                          |

## API design

All endpoints are mounted under `/api` by `app.js`. The full data model behind them is documented on the [Database Schema](/docs/Database-Schema) page.

### Auth

| Method & path                                            | Purpose                                                                                                                     |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/register`                                | Create a Supabase Auth user + row in `users` (and role-specific table: `students`, `tutors`, `educators`, or `organisers`). |
| `GET /api/auth/google`, `POST /api/auth/google/register` | Google OAuth sign-in / registration.                                                                                        |
| `POST /api/auth/login`                                   | Authenticate via Supabase, return session + `{ id, email, name, role }`.                                                    |

### Courses and allocation

| Method & path                                                                                                        | Purpose                                                                                                 |
| -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `GET/POST /api/courses`, `PUT /api/courses/:id`, `DELETE /api/courses/:id`, `PATCH /api/courses/:id/tutors-assigned` | Course records an organiser manages (with venue-clash validation).                                      |
| `GET /api/tutors`, `GET /api/tutors/:id`, `POST /api/tutors`, `PUT /api/tutors/:id`, `DELETE /api/tutors/:id`        | Tutor records.                                                                                          |
| `GET /api/tutors/workload`                                                                                           | Each tutor's assigned hours vs their weekly cap, for the workload spread view.                          |
| `PUT /api/tutors/bulk`                                                                                               | Update a field (weekly hour cap) across all tutors at once.                                             |
| `POST /api/tutors/bulk-rates`                                                                                        | Set hourly rates per academic level across all matching tutors.                                         |
| `PUT /api/tutors/:id/busy-times`                                                                                     | Replace a tutor's imported timetable (busy blocks) wholesale.                                           |
| `GET /api/tutors/:id/assignment-check`                                                                               | Timetable clashes and projected weekly hours if the tutor were assigned to a course.                    |
| `GET/POST /api/tutor-applications`, `PATCH /api/tutor-applications/:id`, `DELETE /api/tutor-applications/:id`        | Tutors applying to tutor a specific course; organiser approval/rejection (with override audit logging). |
| `GET /api/tutor-applications/obvious-fill`                                                                           | Pending applications that can be approved with no judgment call.                                        |
| `POST /api/tutor-applications/bulk-approve`                                                                          | Approve several applications in one action.                                                             |

### Volunteering and sessions

| Method & path                                                        | Purpose                                                                       |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `GET/POST /api/course-volunteers`, `DELETE /api/course-volunteers`   | Students volunteering for overflow course work (with mark threshold check).   |
| `GET /api/course-volunteers/counts`                                  | Number of volunteers per course, for the course list view.                    |
| `PATCH /api/course-volunteers/:id`                                   | Organiser approves/rejects/resets a volunteer.                                |
| `GET/POST /api/session-excusals`, `DELETE /api/session-excusals/:id` | A tutor excusing themselves from one scheduled session of an assigned course. |

### Hours and timesheets

| Method & path                                                                             | Purpose                                                                    |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `GET/POST /api/hour-entries`, `PUT /api/hour-entries/:id`, `DELETE /api/hour-entries/:id` | Logged tutoring hours.                                                     |
| `GET/POST /api/timesheets`                                                                | A tutor's weekly submissions; the organiser's review queue.                |
| `PATCH /api/timesheets/:userId/:weekStart`                                                | Organiser approves/rejects a submitted week.                               |
| `GET /api/timesheets/payroll-export`                                                      | CSV of every approved timesheet with tutor identity, rate and amount owed. |

Timetable PDF parsing is **not** a server endpoint — it happens entirely in the browser via pdf.js + Tesseract.js (see [Integration](#how-this-meets-the-courses-key-requirements)).

## Roadmap

Grouped by the course's Basic / Intermediate / Advanced tiers, with the current state marked.

### Basic (in place)

- Sign up / sign in for all four roles (student, tutor, educator, organiser), via email + password or Google OAuth
- Organiser: create/edit courses, assign tutors (with timetable-clash and weekly-hours checks)
- Tutor: log hours, submit weekly timesheets, view calendar
- Tutor: excuse themselves from a session
- Student: volunteer for overflow course work
- Tutor: apply to tutor a course (mark + availability check, organiser approval flow)
- Timetable import from a PDF via in-browser OCR (pdf.js + Tesseract.js)

### Intermediate

- Automated testing — **done**: Jest suites for the server routes and client storage (`*.test.js`), run by `test.yml` on every push
- Database schema documentation — **done**: [Database Schema](/docs/Database-Schema) page (tables, columns, relationships, ERD)
- Bug tracker — **done**: tasks and bugs are tracked on the team's [Jira board](https://thedevden.atlassian.net/jira/core/projects/TMS/board) (project `TMS`)
- Password reset and account deletion (required by the brief, not yet built)
- Responsiveness/accessibility pass

### Advanced

- Deployment pipeline — **done**: `deploy.yml` ships every push to `main` to Cloudflare Workers automatically
- Performance pass
- Extended stakeholder feedback loop with the assigned client tutor

### Methodology

The team works in Scrum-style sprints aligned to the course milestones (Sprint _n_ = Milestone _n_), with sprint-planning meetings, 2–3 daily scrums per week, and a named Scrum Master / role split. All tasks, bugs and sprint work are tracked on the team's [Jira board](https://thedevden.atlassian.net/jira/core/projects/TMS/board) (project `TMS`), which serves as our Kanban board and issue tracker. Per-sprint meeting minutes are kept in this documentation site as additional process evidence — see [Meeting Minutes — Sprint 1](/docs/meeting-minutes) and [Meeting Minutes — Sprint 2](/docs/meeting-minutes-sprint-2).
