# Backend

How the server side of the app is built: the API, its routes, and the conventions to follow when adding to it.

## Overview

A single hand-written Express API in front of Supabase — every request from the frontend goes through `/api/*` routes we wrote ourselves; nothing in the browser talks to Supabase directly. The same app runs two ways: as a plain Node process locally, and as a Cloudflare Worker in production.

## Tech Stack

- **[Node.js](https://nodejs.org/)** — runtime.
- **[Express 5](https://expressjs.com/)** — routing and middleware.
- **[Supabase](https://supabase.com/)** (`@supabase/supabase-js`) — hosted Postgres for data storage, plus Supabase Auth for sign-up/sign-in (not a hand-rolled JWT system), plus Supabase Storage for the private applicant-transcript bucket.
- **[dotenv](https://www.npmjs.com/package/dotenv)** — loads `.env` locally (Cloudflare Workers gets its environment a different way, via `wrangler` secrets/vars — not covered by `dotenv` in production).
- **[cors](https://www.npmjs.com/package/cors)** — CORS headers.
- **[Google Gemini API](https://ai.google.dev/)** — reads uploaded timetable PDFs for `/api/timetable/parse`, called with plain `fetch` (no SDK dependency).

The timetable-PDF-import feature (calendar page) has two layers. Primary: `public/js/timetable-parser.js` uploads the PDF to `POST /api/timetable/parse`, which sends it to [Google Gemini](https://ai.google.dev/) and replies with the extracted classes as JSON — [External Services](./external-services.mdx) covers the integration. Fallback: when that route can't be reached, the same client module loads [pdf.js](https://mozilla.github.io/pdf.js/) and [Tesseract.js](https://tesseract.projectnaptha.com/) from a CDN and reads the PDF on-device (these exports have no embedded text layer — they're outlined shapes, not real text — so a multimodal model or OCR are the only ways to read them at all).

## Prerequisites

- Node.js 20+
- Access to the project's Supabase project (URL + anon key) — ask a teammate

## Getting Started

Full setup steps (clone, install, `.env`, run) are in [Getting Started](./getting-started.mdx) — this section only covers what's backend-specific.

Environment variables the server reads:

| Variable            | Required | Description                                                                                                                                                                                                |
| ------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SUPABASE_URL`      | Yes      | Your Supabase project's URL                                                                                                                                                                                |
| `SUPABASE_ANON_KEY` | Yes      | The project's anon/public key. **Name matters** — both `app.js` and `server/supabaseClient.js` read this exact variable name; an `.env` using the older `SUPABASE_KEY` name crashes the server on startup. |
| `PORT`              | No       | Defaults to `3000`                                                                                                                                                                                         |
| `GEMINI_API_KEY`    | No       | Google AI Studio key that powers the timetable AI reader (`POST /api/timetable/parse`). Without it the route answers `503` and the calendar page falls back to on-device OCR — nothing else is affected.   |
| `GEMINI_MODEL`      | No       | Overrides the Gemini model used for timetable parsing (defaults to `gemini-3.6-flash`)                                                                                                                     |

There's no separate migration or seed step — the Postgres schema (tables, columns, constraints) is managed directly in the Supabase dashboard's SQL editor, not via migration files in this repo.

```bash
npm start
```

Runs `server.js`, which loads `app.js` (the actual Express app) and serves `public/` as static files, at `http://localhost:3000`.

:::info Shared code across the API/frontend boundary
`public/js/allocation-objectives.js` is written once and loaded twice: the browser pulls it in as a plain `<script>` (exposing the `AllocationObjectives` global the organiser board uses for its preset picker), while `server/routes/tutorApplications.js` `require()`s the same file for the ranked applicants endpoint. It's UMD-wrapped and dependency-free so both environments can share the objective definitions, presets and scoring — one source of truth for how applicants are balanced, not two copies that drift.
:::

:::info Two Supabase clients
`app.js` builds its own Supabase client and attaches it to every request as `req.supabase` (used by `routes/auth.js`). Separately, `server/supabaseClient.js` exports its own instance, imported directly by everything under `server/routes/`. Both read the same env vars, so they behave identically — it's two instantiations rather than one shared one.
:::

## API Conventions

- Every endpoint lives under `/api/*` and is a plain Express route — no framework-generated CRUD, no GraphQL.
- Request/response bodies are JSON (`express.json()` / `express.urlencoded()`) — the two exceptions are the file-upload routes, which take raw bytes instead of multipart (`express.raw`): `POST /api/timetable/parse` (a timetable PDF, `application/pdf`, 15 MB limit) and `POST /api/transcripts/:userId` (an applicant transcript — PDF/PNG/JPEG, 5 MB limit).
- Errors are always `{ "error": "human-readable message" }`, with a status code that means something:
  - `400` — bad/missing input, caught before touching the database
  - `401` — authentication failed (wrong password, no session)
  - `403` — authenticated, but not allowed to do this (e.g. a mark below a course's minimum)
  - `404` — the thing referenced doesn't exist
  - `409` — the write conflicts with the current state: something already exists (duplicate application, taken course code), or the record changed since the caller last read it (see _Conflict resolution on application writes_)
  - `413` — an uploaded file is over its route's size limit
  - `500` — the database/Supabase call itself failed
  - `502`/`503` — an upstream dependency is unavailable: Gemini unreachable (`502`), or transcript storage missing/unconfigured (`503`)
- Internal `/api/*` routes are unversioned — they're small, read top-to-bottom, and change together with the frontend that calls them. The one versioned surface is the public read-only catalogue under `/api/v1/*` ([Public API](./public-api.mdx)), where external consumers need a stable contract. No OpenAPI/Swagger spec anywhere — the docs on this site are the reference.
- Validation (required fields, numeric ranges, business rules like "mark must be ≥ course minimum") happens in the route handler itself, before any database call — never trust the client to have already checked.

### Multi-objective applicant ranking

`GET /api/tutor-applications?courseId=...` ranks a course's applicants by blending five objectives that pull against each other — **merit** (mark), **availability** (free at the tutorial time), **timetable fit** (no clash), **seniority** (academic level) and **headroom** (spare weekly-hour capacity). The strongest applicant is often the most loaded one, so the blend is controllable:

- `?preset=merit` (default) — the historical weighting, where mark dominates. Ordering matches the ranking the system has always used.
- `?preset=balanced` — every objective weighs equally.
- `?preset=fairness` — spare capacity dominates, so work spreads across tutors instead of stacking on the strongest.

An unknown preset gets a `400` listing the valid names. Each applicant's `ranking` object now carries, alongside the familiar facts, the blended `score` (0–100 under the active preset), the normalised `objectives`, `rank` and `meritRank` (position under this balance vs merit-first), `paretoDominated` (another applicant is at least as good on every objective and strictly better on one — true under any weighting), and a `tradeoff` note whenever the two orderings disagree.

### Conflict resolution on application writes

Two organisers can be looking at the same application at the same time. Rather than letting the last save silently overwrite the first, every write to an application declares the state it acted on, and the server refuses stale writes with a `409`:

- `PATCH /api/tutor-applications/:id` requires `expectedStatus` — the status (`pending` / `approved` / `rejected`) the client last saw. If it no longer matches the row, the request is a `409` before anything is written, and the update itself is additionally guarded (`WHERE status = expectedStatus`), so a change landing _mid-request_ still fails instead of overwriting. If the course counter was already bumped before the status write lost its race, the bump is rolled back.
- `PATCH /api/tutor-applications/:id/lock` needs no extra fields — the update is atomic (`WHERE locked = false AND status = 'approved'`), so two simultaneous locks can't both "succeed".
- `POST /api/tutor-applications/bulk-approve` applies the same guards row by row: anything no longer `pending` at execution time (already rejected, or changed mid-request) comes back as `{ success: false, error: "Someone else already changed this application" }` with its counter bump rolled back, while the rest still go through. The board surfaces these as "something changed since you opened this".

This is optimistic concurrency: no locks and no version columns — just conditional updates that only land on the state they were based on. Any `409` in this flow means "someone got there first": reload the list and try again against the fresh state. `server/testUtils/fakeSupabase.js` accepts an optional fourth `hooks` argument (`onBeforeResolve`) so tests can interleave a competing writer between a route's read and its write and prove these paths.

## Development Guide

### Branching & commit conventions

Follows the team's GitHub methodology: commits as `type: short description` (`feat`, `fix`, `docs`, `style`, `refactor`, `chore`), one logical change per commit. Feature work happens on `feature/<name>` / `bugfix/<name>` branches, merged via a reviewed pull request.

### Code style / formatting

```bash
npm run format         # auto-fix formatting across the whole repo
npm run format:check   # check only, no writes — what CI runs
```

Prettier only, default config. No linter is configured.

### Adding a new route

Add the file under `server/routes/`, `require` the shared client from `server/supabaseClient.js` (don't create a new client instance), and mount it in `app.js` alongside the existing `app.use('/api/...', ...)` lines.

## Deployment

The same `app.js` runs two ways:

```bash
npm start        # server.js — plain Node process, express.static serves public/
npm run dev:worker  # wrangler dev — local Cloudflare Workers runtime
npm run deploy      # wrangler deploy — ships to Cloudflare Workers
```

In the Workers build, static files in `public/` are served by Cloudflare's assets layer (configured in `wrangler.toml`) instead of `express.static`.

CI runs on **Gitea Actions** (`.gitea/workflows/`), not GitLab CI — `sdp.ms.wits.ac.za` is a self-hosted Gitea instance, so the `.gitlab-ci.yml` file in the repo root is inert and never runs; ignore it. Four workflows:

- `format.yml` — Prettier check (`npm run format:check`) on every push.
- `test.yml` — Jest suite (`npm test`) on every push.
- `deploy.yml` — deploys the app to Cloudflare Workers via `wrangler deploy` on push to `main`.
- `docs-deploy.yml` — builds this documentation site and deploys it to Cloudflare Pages, on push to `main` when something under `my-docs/` changes.

:::danger Open security item
Every Supabase table currently has Row Level Security **disabled**. Supabase auto-generates a full REST API for every table via PostgREST — with RLS off, anyone holding the anon key (which is unavoidably public, it ships in the browser) can read and write every table directly, completely bypassing this hand-written API. This has been confirmed live: it's possible to pull every user's real name, email and role straight from Supabase with nothing but the anon key.

Fix, not yet done: re-enable RLS on every table, and switch `server/supabaseClient.js` / `app.js`'s Supabase client to a `service_role` key (bypasses RLS, must never be sent to a browser) so the server keeps working exactly as-is while the direct public API gets locked out.
:::
