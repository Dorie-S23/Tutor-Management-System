# Getting Started

How to get the project running locally.

## Prerequisites

- **Node.js 20+** and npm
- Access to the project's **Supabase** project (URL + anon key) — ask a teammate, or point at your own Supabase project for local testing

## 1. Clone and install

```bash
git clone https://sdp.ms.wits.ac.za/the-devden/Tutor-Management-System.git
cd Tutor-Management-System
npm install
```

## 2. Configure environment variables

Copy the example file and fill in real values:

```bash
cp .env.example .env
```

```
SUPABASE_URL=
SUPABASE_ANON_KEY=
GEMINI_API_KEY=
PORT=3000
```

- **`SUPABASE_URL`** / **`SUPABASE_ANON_KEY`** — from your Supabase project's **Settings → API**. The variable name matters: both `app.js` and `server/supabaseClient.js` read `SUPABASE_ANON_KEY` specifically — an `.env` with the older `SUPABASE_KEY` name will crash the server on startup with `Missing SUPABASE_URL or SUPABASE_ANON_KEY environment variables`.
- **`GEMINI_API_KEY`** — a Google AI Studio key, used only for reading uploaded timetable PDFs (`POST /api/timetable/parse`). Optional: without it that route answers `503` and the calendar page falls back to on-device OCR.
- **`PORT`** — defaults to `3000` if omitted.

`.env` is gitignored and never committed — each teammate keeps their own.

## 3. Create the transcript storage bucket (one-off)

Tutor and volunteer applications require an uploaded transcript, which is kept in Supabase Storage — so each Supabase project needs a private `transcripts` bucket once:

1. **Storage → New bucket.** Name it `transcripts` and leave **Public bucket off** — files are only ever handed out as short-lived signed URLs.
2. **Give the anon role access to it** (Storage → Policies → New policy for this bucket, or the SQL editor):

   ```sql
   create policy "transcripts access"
   on storage.objects for all
   to anon
   using (bucket_id = 'transcripts')
   with check (bucket_id = 'transcripts');
   ```

   The server talks to Storage with the anon key (`server/supabaseClient.js`), so without this step uploads come back as unauthorized — the same key-everything model the rest of the app currently runs on (see the open RLS item in [Backend](./backend.mdx#deployment)).

Skip this if you're only working on pages that don't upload transcripts. Without the bucket, a transcript upload answers `503` _"Transcript storage isn't set up yet…"_ — and since every application needs a transcript on file, applying stays blocked until the bucket exists, instead of failing silently.

## 4. Set up organiser access (one-off)

Organiser accounts are approved, not free to use: every organiser sign-up files a request that the **super-organiser** approves or denies on the **Organiser Requests** page (`organiser-requests.html`). Two one-off pieces make that work in a fresh Supabase project:

1. **Create the `organiser_requests` table** (SQL editor):

   ```sql
   create table organiser_requests (
     id bigint generated by default as identity primary key,
     user_id uuid not null references users(id),
     course_id smallint not null references courses(id),
     status text not null default 'pending',
     created_at timestamptz not null default now(),
     reviewed_at timestamptz,
     reviewed_by uuid references users(id)
   );
   ```

2. **Promote the super-organiser** — the one account that reviews requests and sees every course — by updating its `users.role` (SQL editor):

   ```sql
   update users set role = 'super_organiser' where email = 'admin@wits.ac.za';
   ```

Without a super-organiser account nobody can approve requests — new organisers stay blocked at sign-in with _"Your organiser request is still awaiting approval…"_. Organisers registered before this existed have no request rows and keep full access, so an existing deployment only needs the table plus the promoted account.

## 5. Run it

```bash
npm start
```

This runs `server.js`, a thin entry point that loads `app.js` (the actual Express app and all its routes) and serves `public/` as static files. Visit **http://localhost:3000** — it redirects to the login page.

## 6. (Optional) Run the Cloudflare Worker variant

The same `app.js` also runs as a Cloudflare Worker via [Wrangler](https://developers.cloudflare.com/workers/wrangler/), with `worker.js` as the entry point instead of `server.js` (static assets are served by Cloudflare's assets layer there instead of `express.static`):

```bash
npm run dev:worker   # wrangler dev — local Workers runtime
npm run deploy       # wrangler deploy
```

## 7. Formatting

```bash
npm run format         # auto-fix formatting across the repo
npm run format:check   # check only, no writes
```

CI runs `format:check` on every push (see `.gitea/workflows/format.yml`) — pushing unformatted code fails the pipeline before anything else runs.

## 8. Run this documentation site

This site is a separate app with its own `package.json`:

```bash
cd my-docs
npm install
npm start
```

## Project structure

```
Tutor-Management-System/
├── app.js                     # Express app: middleware + every route mounted here
├── server.js                  # Node entry point — requires app.js, serves public/, listens
├── worker.js                  # Cloudflare Workers entry point — same app.js
├── routes/
│   └── auth.js                 # /api/auth/register, /api/auth/login (Supabase Auth)
├── server/
│   ├── supabaseClient.js       # shared Supabase client used by server/routes/*
│   └── routes/
│       ├── courses.js
│       ├── tutors.js
│       ├── hourEntries.js
│       ├── courseVolunteers.js
│       └── tutorApplications.js
├── public/
│   ├── html/                   # one .html file per page
│   ├── css/
│   └── js/                     # one script per page, plus shared helpers (nav.js, storage.js, ...)
├── models/User.js              # plain User data class
├── my-docs/                     # this documentation site (independent Docusaurus app)
└── .gitea/workflows/            # format-check, app-deploy, docs-deploy pipelines
```

:::info Two Supabase clients
`app.js` builds its own Supabase client and attaches it to every request as `req.supabase` (used by `routes/auth.js`). Separately, `server/supabaseClient.js` exports its own client instance, imported directly by everything under `server/routes/`. Both read the same `SUPABASE_URL`/`SUPABASE_ANON_KEY`, so they behave identically — it's just two instantiations instead of one shared one.
:::

## Troubleshooting

- **`Missing SUPABASE_URL or SUPABASE_ANON_KEY environment variables`** on startup — check the exact variable name in your `.env` matches `.env.example`. This has bitten the team before after a merge silently renamed the expected variable.
- **Login returns `401 Invalid login credentials`** — either the account was never actually registered (go through `register.html` first), or the email/password doesn't match what was registered. Check the Supabase dashboard's **Authentication → Users** if you're not sure an account exists.
- **Uploading a transcript returns `503` _"Transcript storage isn't set up yet…"_** — the `transcripts` bucket hasn't been created in this Supabase project yet; see step 3 above, which also adds the anon access policy uploads need.
